# The hosted MCP server and the website

The MCP server of Agentic SEO Check as a Cloudflare Worker, at `https://mcp.agentic-seo.rivi.software/mcp`, run by RIVI Software and free to use ([issue #35](https://github.com/rivi-software/agentic-seo-check/issues/35)). A second Worker, `agentic-seo-check-site`, serves the project's website at `https://agentic-seo.rivi.software`, with a page and site audit to run in the browser and a share link for each report ([issue #39](https://github.com/rivi-software/agentic-seo-check/issues/39), [issue #45](https://github.com/rivi-software/agentic-seo-check/issues/45), [issue #54](https://github.com/rivi-software/agentic-seo-check/issues/54)). The README's [Hosted server](../README.md#hosted-server) section is for its users; this page is for running it. It is not part of the npm package: `hosted/` is outside `files`.

## How it works

Each POST to `/mcp` builds an MCP server with `createMcpServer({ hosted })` (`src/mcp-hosted.ts`) and answers it with the SDK's `WebStandardStreamableHTTPServerTransport`, stateless and in JSON. Wrangler bundles `src/` from the same commit; `playwright`, `lighthouse` and `chrome-launcher` resolve to `src/unavailable.ts`, so the bundle leaves them out.

The MCP server and the website are two Workers, each with its own hostname, `MODE` and secrets, which deploy together ([Deploys](#deploys)). They share their limits: the website's configuration has the MCP server's rate limiting namespaces, and binds its Durable Object.

- `wrangler.jsonc`: the MCP server's Worker, `agentic-seo-check-mcp`: its Custom Domains, the rate limits, the Durable Object, the Analytics Engine dataset, the daily Cron Trigger, the build command that copies posthog-js's browser build (`scripts/posthog-js.ts`), and the variables `MODE`, `DAILY_REQUESTS`, `CALLER_SITES`, `PLATFORM_SITES`, `STATE_JURISDICTION`, `OPENAI_APPS_CHALLENGE` and `POSTHOG_HOST`.
- `wrangler.site.jsonc`: the website's Worker, `agentic-seo-check-site`, from `src/site/worker.ts`: its Custom Domain, the same rate limits and dataset, the MCP server's Durable Object (`script_name`), the secrets a deploy requires (`TURNSTILE_SECRET_KEY`, `WEB_BOT_AUTH_KEYS`, `SHARE_KEY`), and the variables `MODE`, `DAILY_REQUESTS`, `CALLER_SITES`, `PLATFORM_SITES`, `STATE_JURISDICTION`, `TURNSTILE_SITE_KEY` and `POSTHOG_HOST`. `test/configs.test.ts` holds what the two share equal.
- `src/index.ts`: the routes (`/mcp`, `/`, `/crawler`, `/robots.txt`, `/favicon.svg`, `/.well-known/http-message-signatures-directory`, `/.well-known/openai-apps-challenge`), CORS, and the Cron Trigger that fetches OpenAI's ChatGPT connector ranges. `mcp.agentic-seo-check.rivi.software`, the MCP server's hostname in 0.7.0, still answers at `/mcp`, so clients set up with it keep working, and sends every other path to `mcp.agentic-seo.rivi.software` with a 301.
- `src/limits.ts`: the limits per caller, per platform, per site and per day, the daily cap on the different sites each caller audits ([issue #73](https://github.com/rivi-software/agentic-seo-check/issues/73)), and one Analytics Engine record per tool call. The URL rules, the caps, the answers that count as a site refusing the server, and the gate that obeys robots.txt (and, in a crawl, `Crawl-delay`) before every request are in the core, `src/core/hosted.ts` (`hostedFetch`), so the npm package's tests cover them too.
- `src/signing.ts`: Web Bot Auth ([issue #41](https://github.com/rivi-software/agentic-seo-check/issues/41)). Every https request to a site is signed with the first Ed25519 key of the Worker secret `WEB_BOT_AUTH_KEYS`, as HTTP Message Signatures (RFC 9421) over `@authority` and `Signature-Agent: "https://mcp.agentic-seo.rivi.software"`, and the key directory lists each key's public half, signed by that key. Without the secret the requests go out unsigned and the directory answers 404.
- `src/analytics.ts`: the usage analytics of `/mcp` ([issue #57](https://github.com/rivi-software/agentic-seo-check/issues/57)). `src/telemetry/mcp.ts`, in the core, watches the transport, and this sends one `$mcp_tool_call` event per tool call and one `$mcp_initialize` per `initialize` to PostHog's EU project "Agentic SEO", with `ctx.waitUntil`, after the answer: the tool, whether it failed and how, the duration, the MCP client (its name and version, and the product token at the start of its `User-Agent` and `X-Anthropic-Client` headers, such as `claude-user`), the platform, and the outcome, requests and pages of the call's record. The tools add what the call did ([issue #84](https://github.com/rivi-software/agentic-seo-check/issues/84), `src/mcp-hosted.ts`, through `noteCall`): `target` (`url` or `html`), the audit's `score`, `errors`, `warnings`, `infos` and `rules` (the ids that fired, as the CLI's `cli_command` lists them), a re-check's `baseline_fixed`, `baseline_open` and `baseline_new`, the `format`, `detail` and `page_detail` it ran with, `recheck` (it gave `baseline`), and `reason`, from a fixed list, when a limit kept it out (`caller_calls`, `platform_crawls`, `daily_requests`, `caller_sites`, `paused` …), a refusal stopped it (`robots_txt`, `robots_unreadable`, `crawl_delay`, `http_403`, `http_429`, `challenge`, `site_requests`) or the address rules turned its URL away (`address`). A crawl that a refusal stops partway answers with the pages it read and `site.crawl-stopped` (`aeo.crawl-stopped`) in `rules`, so its call is no error, and it still carries the refusal's `reason`: the crawl tells the gate (`RequestGate.crawlStopped`, [issue #94](https://github.com/rivi-software/agentic-seo-check/issues/94)). The transport adds `arguments`, the names of the arguments the call gave that its tool has (`HOSTED_TOOLS`), and the optional `context` an agent writes on what the call is for, as `$mcp_intent` with `$mcp_intent_source: context_parameter`, cleaned as an error's message is (`intentOf`, `cleanMessage`: URLs, paths, quoted text, hostnames in any script such as `bäckerei-müller.de`, emails, and IPv4 and IPv6 addresses), with the tool's own rule ids kept. The audit tools list `context` as required, as PostHog's SDK does, but a call without it, or with one that is not text or too long, still works (`noContext` in `src/mcp-hosted.ts`). With [issue #101](https://github.com/rivi-software/agentic-seo-check/issues/101) the transport also adds `$mcp_input_keys` (`arguments`, and `[redacted]` once when the call gave others), `$mcp_tool_description`, and `$mcp_llm_model` with `$mcp_llm_model_source`: Codex's `x-codex-turn-metadata.model` in `_meta` (`client_metadata`), or the agent's `llm_model` (`self_reported`), kept only in a model id's shape (`modelIdOf`). A call to a tool the server lacks is a `$mcp_unknown_tool` event, its name kept when it has a tool name's shape and `other` otherwise (`toolNameOf`); `send_feedback` is a `$mcp_feedback` event rather than a tool call, with `$mcp_feedback_type`, `_summary`, `_details`, `_friction_points`, `_suggested_improvement`, `_tool`, `_sentiment` and `_task_completed` (`_tool` is one of the server's tools, or `other`), each text cleaned as `context` is and cut to 1,000 characters, and the summary and details as `$mcp_intent`. Every event carries `$mcp_interface: mcp`. Never the hostname, an argument's value, the answer or the caller's address. A connection's calls share a session, as PostHog's own SDKs do it for a stateless server: the answer to `initialize` carries a session token in `Mcp-Session-Id` (the session's id, and the client's name, version and protocol revision, in base64url JSON), which the client sends back with each request, so the calls name their client too. A conversation's calls share one across connections (issue #101): each answer ends with `{"conversation_id":"…"}`, a UUIDv7, which the agent sends back as `conversation_id`; a call that sends none back gets its connection's session id, and one that has neither a new id, so a made-up value never joins two callers. A call's event carries it as `$mcp_conversation_id`, and its session is `ses_` and the conversation's id. The Worker keeps nothing; a client that sends no token back and an agent that sends no conversation back get a session per call. `$mcp_initialize` carries the session's id as `distinct_id` but no `$session_id`, so a connection that calls no tool, such as a chat that loads the connector and never uses it, counts no session. It also sends an `$exception` event ([issue #60](https://github.com/rivi-software/agentic-seo-check/issues/60), `src/telemetry/exceptions.ts`) for a tool's internal failure, for the 500 the Worker answers when a request throws, and for a failure of the website's form that is not the site's refusal: the error's type, its message with URLs, paths, quoted text and hostnames taken out, its stack, `route` (such as `server:/mcp`, `server:cron` or `website:/share/:result`, never the address) and, for a tool call, the tool and the call's session. Since [issue #93](https://github.com/rivi-software/agentic-seo-check/issues/93), the MCP server's Worker also hears what the core catches (`hearCaughtError`, set with `onCaughtError`): a rule that throws (`rule`), a page a crawl leaves out, and a request it could not sign (`task: request_signature`). A call's errors go in the request of its `$mcp_tool_call`, one event per bug with `occurrences`, 10 at most, and carry what that event says of the client (`$mcp_client_name` …), `arguments`, `format`, `detail`, `page_detail`, `recheck`, `target`, `platform`, `outcome`, `requests`, `pages` and `$mcp_duration_ms`, never `$mcp_intent` or what the audit found. Only a `CallLimitError` is a limit: any other error of `startCall`, such as the Durable Object's, is an `internal` failure with an `error` record, and an error a tool's callback throws after its work is `internal` too, not the SDK's `validation`. Work after the answer reports its failures with a `task`: `request_count` (the day's count), `call_record` (Analytics Engine, or a call's `end`), `openai_ranges` (also from the Cron Trigger, as `server:cron`) and `signing_keys` (a `WEB_BOT_AUTH_KEYS` that does not parse, as a `SigningKeysError` with a fixed message, once per isolate). The 500 sits in the session of the request's `Mcp-Session-Id`, when it holds one. The website's Worker sets the same listener ([issue #96](https://github.com/rivi-software/agentic-seo-check/issues/96)): a run of the audit form keeps what the core catches within it (`inRun`) and, when it ends, sends those errors and the one that ended it in one request (`reportRun`), one event per bug, with `route: "website:/audit"`, `tool` (`web_audit_page` or `web_crawl_site`), and the `outcome`, `requests` and `pages` of its record. A crawl's run ends after its answer has streamed. Only a `CallLimitError` is a 429 there too: any other error of `startCall` is reported, recorded as `error` and answered with a 503. A run that fails is `refused` (502) when the site kept it out, by its answer or by its robots.txt (an `ExpectedError`), and `error` (500) otherwise, which the page words as "The audit failed on our side, not yours. Try again in a minute.", with nothing of the error; `audit_failed` sends that kind as its `reason`. `POSTHOG_HOST` empty turns it off, and `/ph.js` with it: `.dev.vars` empties it for `hosted:dev` and `site:dev`, and the workerd tests point it at a host of their own.
- `src/callers.ts`: who is calling. claude.ai and ChatGPT call from their platforms' address ranges and count as one caller each, with ten times the limits. Each isolate reads OpenAI's ranges from the Durable Object at most once an hour; while the object has none, as a new one has until the Cron Trigger runs at 03:17 UTC, an isolate fetches the list itself, once an hour at most, after its answer.
- `src/state.ts`: the Durable Object that counts the day's requests, keeps the sites each caller audited today, and keeps OpenAI's ranges. A site is a hostname without `www.`; a call that requests one counts it once a day (a page audit also counts the hostname its page redirects to, a subdomain included), after the other limits let the call through, and a caller may audit its sites of the day again and again. The object stores neither the caller's key nor the hostname, only their HMAC-SHA256 with a random key made on the day's first call, and an alarm deletes the day's rows and its key at 00:00 UTC. It is the MCP server's Worker's, and the website's binds it, so the form's runs count in the same day, and it runs the code the MCP server last deployed. There is one object, named `global`, in the `eu` jurisdiction ([issue #78](https://github.com/rivi-software/agentic-seo-check/issues/78)): it runs and keeps its data in the EU, while Workers anywhere call it, and only its ID is logged outside the EU. Both Workers ask for it through `globalState`, with `STATE_JURISDICTION` `eu` in both configurations; workerd has no jurisdictions, so `.dev.vars` sets `none` for local runs and the workerd tests, and any other value keeps the object in the EU.
- `src/pages.ts`: the landing page and the page for site owners, which the User-Agent links to. Both state the limits from `wrangler.jsonc`.
- `src/ui/`: the look both hostnames share, RIVI Software's as rivi.software has it (dark, Geist and Geist Mono, the signal green). `frame.ts` is the frame of every page (the head, the header and the footer, which link the two hostnames), `style.ts` the stylesheet, `icons.ts` the icons, `og.ts` the words of each hostname's share image, and `assets.ts` serves the fonts and the share images. `share-card.ts` draws a shared result's image as SVG, which resvg (`@resvg/resvg-wasm`) turns into a PNG, and `share-image.ts` loads resvg's WebAssembly and the card's fonts; only the routes import it, as only they import `assets.ts`. `assets/` holds the fonts, Latin subsets of Geist and Geist Mono, with their licence (SIL OFL 1.1); the static instances of Geist 400, 500 and 600 and Geist Mono 400 that a shared result's image is set in, cut to ASCII and `… · – — ’` (`geist-*-ascii.ttf`), since resvg reads neither WOFF2 nor a variable font's weights (they come from the `geist` package on npm, cut with `uvx --from fonttools pyftsubset <font>.ttf --unicodes="U+0020-007E,U+00B7,U+2013,U+2014,U+2019,U+2026" --layout-features="kern,liga,calt"`); and the share images, `og-site.png` and `og-mcp.png`, which each hostname serves at `/og.png`. `pnpm run hosted:og` draws them again with Playwright, as rivi.software's cards are drawn (`scripts/og-image.ts`): run it after changing a card in `og.ts`, and commit the PNGs.
- `src/site/`: the website, which its own Worker serves at `agentic-seo.rivi.software`: `worker.ts` is its entry, and `routes.ts` has its routes (`/`, `/rules`, `/audit`, `/share/…`, `/robots.txt`, `/sitemap.xml`, `/llms.txt`, `/site.js`, the fonts) and the Content-Security-Policy; `home.ts` and `rules-page.ts` the pages, in the frame of `layout.ts`; `audit.ts` answers the audit form; `report.ts` renders a page's two audits as HTML and `site-report.ts` a site's, as cards in sections that the pages' script shows one at a time behind tabs, and that print (or save as a PDF) one after another on white, by the print rules at the end of `src/ui/style.ts`, with everything quoted from the audited site escaped; `share.ts` signs and opens share links, and `share-page.ts` renders the report's Share menu and the page a link opens; `files.ts` holds robots.txt, the sitemap, llms.txt and the pages' script, which the hosted server's pages load too, from their own hostname. On the production hostnames the script loads posthog-js from `/ph.js` (`src/ui/posthog-script.ts`: the ES module build that loads no other script, which `scripts/posthog-js.ts` copies to `.generated/posthog-js.txt` before each build, since Wrangler bundles a `.js` file as code) and sends pageviews and a closed list of events: `audit_requested`, `audit_shown` (the kind and the scores), `audit_failed` (a fixed reason), `report_downloaded` (`json`, `markdown` or `pdf`), `report_shared`, `snippet_copied` and `link_clicked`. Before an event leaves, a share link's result and the `?url=` of the form are taken out of every address, and the page title with them. Visitors are counted without a cookie until they accept one in the banner (`frame.ts`); Do Not Track and Global Privacy Control count as a decline. There is no autocapture, replay, heatmap or survey.
- `scripts/wrangler.ts`: runs Wrangler in this directory with the defines a build needs (`scripts/defines.ts`): the npm package's version and the rate limits of the configuration it runs (`--config`, `wrangler.jsonc` without one).

## Commands

From the repository's root:

```bash
pnpm run hosted:dev      # run the MCP server locally in workerd, at http://localhost:8787
pnpm run site:dev        # run the website locally, at http://localhost:8788, beside hosted:dev
pnpm run hosted:check    # generate the MCP server's types (worker-configuration.d.ts), then typecheck both
pnpm run hosted:build    # bundle the MCP server as a deploy does, into hosted/dist
pnpm run site:build      # bundle the website as a deploy does, into hosted/dist/site
pnpm run hosted:test     # their limits and pages in Node, and both bundles in workerd
pnpm run hosted:deploy   # deploy the MCP server (needs CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID)
pnpm run site:deploy     # deploy the website (the same)
pnpm run hosted:secret <NAME>  # set a secret of the MCP server's Worker; site:secret the website's
pnpm run --silent hosted:key  # print a new Web Bot Auth key for the secret WEB_BOT_AUTH_KEYS
```

Run `site:dev` in a second terminal while `hosted:dev` runs: the website's Durable Object binding names the MCP server's Worker, which Wrangler finds through its local dev registry, and without it the form refuses with "Worker "agentic-seo-check-mcp" not found". One `wrangler dev` with both configurations does not do: Wrangler hands the defines to the first Worker only. Each answers as its own hostname, the first of its routes, so a local form's `Origin` is `http://agentic-seo.rivi.software`. `.dev.vars` holds Cloudflare's public Turnstile test keys, which pass every check, so the form works locally, and the Ed25519 test key of RFC 9421, so requests are signed locally with a key nobody trusts. It sets `STATE_JURISDICTION` to `none`, since workerd says "Jurisdiction restrictions are not implemented in workerd": the local Durable Object has no jurisdiction.

`pnpm run verify` runs `hosted:check`, `hosted:build`, `site:build` and `hosted:test` after the package's own checks. Run Wrangler through these scripts, not on its own: a bundle without the defines does not start.

## The audit form

`POST /audit` on the website's hostname runs the SEO audit and the AEO audit of one URL and answers with the homepage and the report. It uses no model and stores nothing. Before it requests anything it checks, in this order: that the form came from the site's own page (the `Origin` header), that the address is one the hosted server may request (`hostedUrlProblem`), that Cloudflare Turnstile gave the form's token, and the limits of `src/limits.ts`, where a run counts as one call of its IP address. Its requests go through the hosted gate, as a tool call's do, and it writes the same Analytics Engine record, with `web_audit_page` as the tool. A GET never audits: `/?url=…` fills the field only.

An address with no path and no query is a site's homepage, and the form crawls the site from it ([issue #45](https://github.com/rivi-software/agentic-seo-check/issues/45)): with the caps of `seo_crawl_site`, obeying robots.txt and `Crawl-delay`, as a crawl in the limits (one of the 3 a minute per address, and one of its 10 sites a day) and with `web_crawl_site` as the tool in its record. One crawl gives both audits (`auditSiteBoth` in `src/core/aeo/audit.ts`), so no page is requested twice. A crawl takes tens of seconds, so its answer streams: it waits for the crawl's first page, so that a site refusing it from the start gets a refusal with its status, then sends the page up to the report, a line for each step of the crawl, and the report. A crawl that fails after that says why in the page, with status 200. The stylesheet hides the progress once the report follows it. With `MODE` `no-crawls`, a homepage gets the page audit, and its report says crawls are off.

The form is off, and says so, while `TURNSTILE_SITE_KEY` or `TURNSTILE_SECRET_KEY` is missing, and when `MODE` is `closed`.

## Share links

Each report has a Share button ([issue #54](https://github.com/rivi-software/agentic-seo-check/issues/54)): a menu with X, LinkedIn and Bluesky, each the network's own page for a new post with the text and the link filled in, the link to copy, and the system's share sheet where the browser has one. The site keeps no report, so the link holds the result itself: `/share/<result>.<signature>`, where `<result>` is the address, the day of the audit, both scores and their counts, and a site's number of pages, in base64url, and `<signature>` is 128 bits of an HMAC-SHA256 of it with the Worker secret `SHARE_KEY`. A link that no key signed gets the 404 page, so a link cannot claim a score the audit did not give, and the image is only drawn for results the form produced.

- `/share/<result>.<signature>` is the page a link opens: the address, the day and the two scores, with the form filled with the address one click away. It is `noindex`, and robots.txt leaves `/share/` open, since X, LinkedIn and Bluesky fetch it and its image to draw the card.
- `/share/<result>.<signature>.png` is its 1200×630 image, with the hostname (never the path), the kind of audit, the day and both scores. A result's image never changes: it is served as `immutable` and kept in the Cache API, so each Cloudflare location draws it once. resvg starts on an isolate's first image, not when the Worker starts.

Opening a link requests nothing from the audited site and writes no record. Without `SHARE_KEY`, reports have no Share button. `.dev.vars` has made-up keys for local runs and the tests.

## Deploys

[`deploy-hosted.yml`](../.github/workflows/deploy-hosted.yml) deploys both Workers with each push to `main` that changes what their bundles are built from (`src/`, `hosted/` but its tests and docs, `package.json`, the lockfile), in one job: the MCP server first, then the website. A release is such a push too: its version commit changes the version in `package.json`, which both bundles carry. So a fix reaches both as soon as it is merged, before the release that brings it to npm; between releases they run `main` under the last release's version number. A change to a limit or `MODE` goes live when it is merged.

Run **Deploy the hosted server** by hand on `main` to deploy both again, after a failed run for instance. To roll both back, run it on an earlier release tag from v0.13.0 on (`gh workflow run deploy-hosted.yml --ref v0.13.0`), which runs that tag's workflow on that tag's code. An earlier tag has no Worker of its own for the website, and its MCP deploy takes `agentic-seo.rivi.software` back to the MCP server's Worker. The next push to `main` that changes a bundle deploys `main` again.

The job runs in the GitHub environment `hosted`, which holds the Cloudflare token, so no other job sees it. A run deploys the commit it runs on and refuses any ref but `main` and release tags, so no input can hand the token other code. A push while a deploy runs waits for it, and of the pushes waiting only the newest deploys, since it carries the others' changes.

The website binds the MCP server's Durable Object, which runs the code the MCP server last deployed. The job deploys the MCP server first and the website straight after, and never the website when the MCP server's deploy failed, so the website's code never runs ahead of the object's. For the seconds in between, and when the website's deploy fails, the website's previous code calls the new object: keep the object's methods additive. Both Workers ask for the object through `globalState` in `src/state.ts`, from the same commit, so the two never count in different objects.

Each Worker has its own `MODE`. The MCP server's (`wrangler.jsonc`) is `open`, `no-crawls` (crawls are refused, single page audits work) or `closed` (every tool call is refused, with the local server as the way out); the website's (`wrangler.site.jsonc`) is `open`, `no-crawls` (the form audits a homepage alone) or `closed` (the form is off). To pause both, change both and merge the change.

## Setting it up

Once, before the first deploy:

1. **Workers Paid** on the Cloudflare account, for the CPU an audit needs (the Free plan stops a request at 10 ms).
2. **A Cloudflare API token** for deploys: start from the *Edit Cloudflare Workers* template, and limit it to the account and the `rivi.software` zone. Cloudflare cannot limit a token to one Worker; the GitHub environment keeps it from every other job.
3. **The GitHub environment `hosted`**, with the secret `CLOUDFLARE_API_TOKEN` and the variable `CLOUDFLARE_ACCOUNT_ID`. Limit its deployment branches and tags to `main` and `v*`.
4. **The hostnames free:** a Custom Domain cannot be created where `mcp.agentic-seo.rivi.software` or `agentic-seo.rivi.software` already has a CNAME record. The first deploy creates the DNS records and the certificates.
5. **A billing notification** on the account, for usage past what Workers Paid includes.
6. **A privacy notice and terms of use** on rivi.software (#33 needs their URLs too). The landing page states what the server records and for how long; the privacy notice should say the same, and name Cloudflare as processor, and PostHog for the analytics (issue #57).

7. **A Turnstile widget** for the audit form, done on 2026-11-10: the widget "agentic-seo-check website audit form" for the hostname `agentic-seo.rivi.software` (its hostnames list it), with the mode *Invisible*. Its site key is `TURNSTILE_SITE_KEY` in `wrangler.site.jsonc`, and its secret key is the website's Worker secret `TURNSTILE_SECRET_KEY`, which stays through later deploys. To replace it, rotate the secret in the Cloudflare dashboard (Turnstile) and run `pnpm run site:secret TURNSTILE_SECRET_KEY`.

8. **A Web Bot Auth key, and Cloudflare's verified bots** ([issue #41](https://github.com/rivi-software/agentic-seo-check/issues/41)):
   1. Make a key with `pnpm run --silent hosted:key`, which prints the secret's value, a JSON list of one private JWK, and writes nothing to disk. Keep it where you keep secrets: Cloudflare never shows a secret again.
   2. Set it with `pnpm run hosted:secret WEB_BOT_AUTH_KEYS` and paste the value, then deploy. The website's form sends its requests as the MCP server does, so set the same value with `pnpm run site:secret WEB_BOT_AUTH_KEYS`. Check `https://mcp.agentic-seo.rivi.software/.well-known/http-message-signatures-directory`: it lists the public key, and Cloudflare's `http-signature-directory` tool (crates.io) validates it.
   3. In the Cloudflare dashboard, open the Bot Submission Form (Application security, BotBase, or Manage Account, Configurations), and submit: verification method *Request Signature*; under *Validation Instructions* the directory's URL; the categories *SEO* and *Agent*; `https://mcp.agentic-seo.rivi.software/crawler` as the bot's documentation. If the form asks for a User-Agent pattern, give `agentic-seo-check/` with `+https://mcp.agentic-seo.rivi.software/crawler`, which only the hosted server sends: the local tool's token is `agentic-seo-check-local`. Its status is under BotBase, History.
   4. Once accepted, `https://crawltest.com/cdn-cgi/web-bot-auth` answers a signed request with 200 (401 while the key is unknown).

   To rotate the key, make a new one, set the secret of both Workers to a list of the new key and the old (`[new, old]`), deploy both, and ask Cloudflare to rotate the registration; once it has, set the new key alone on both. The key directory, on the MCP server's hostname, lists the MCP server's secret.

9. **A key for share links** ([issue #54](https://github.com/rivi-software/agentic-seo-check/issues/54)): `openssl rand -base64 32 | pnpm run site:secret SHARE_KEY`, then deploy the website. Reports have a Share button from then on. To rotate it, set the old value as `SHARE_KEY_PREVIOUS` first, then a new `SHARE_KEY`: the Worker checks links with both and signs with `SHARE_KEY` only, so the links made before keep working. A key that has leaked goes, without becoming `SHARE_KEY_PREVIOUS`; its links then get the 404 page.

10. **PostHog** ([issue #57](https://github.com/rivi-software/agentic-seo-check/issues/57)): the project "Agentic SEO" on PostHog Cloud EU, whose public token is `POSTHOG_TOKEN` in `src/telemetry/posthog.ts`. In its settings, turn on *Web analytics, Cookieless tracking*: without it PostHog discards every website event sent before a visitor accepts the cookie. Keep *Discard client IP data* on. Under *Error tracking*, add an alert for a new issue ([issue #60](https://github.com/rivi-software/agentic-seo-check/issues/60)), to email or Slack.

11. **The website's Worker**, before the first deploy of `wrangler.site.jsonc`, which fails while one of its required secrets is missing:
    1. Set its secrets; the first creates the Worker (Wrangler asks). `TURNSTILE_SECRET_KEY` is the widget's secret key, which the Turnstile page of the dashboard shows; `WEB_BOT_AUTH_KEYS` and `SHARE_KEY` are the values the MCP server's Worker has, so the form's requests are signed with the registered key and the share links made before keep working; set `SHARE_KEY_PREVIOUS` too if the MCP server's Worker has one.

       ```bash
       pnpm run site:secret TURNSTILE_SECRET_KEY
       pnpm run site:secret WEB_BOT_AUTH_KEYS
       pnpm run site:secret SHARE_KEY
       ```

    2. Merge to `main`. **Deploy the hosted server** deploys the MCP server, which drops `agentic-seo.rivi.software` from the MCP server's Worker (a deploy sets a Worker's whole list of Custom Domains), and then the website, seconds later in the same job, which takes it, as Wrangler does for a deploy without a terminal.
    3. Once the MCP server's Worker no longer has the website's route, delete from it the secrets only the website reads: `pnpm exec wrangler secret delete TURNSTILE_SECRET_KEY --config hosted/wrangler.jsonc`, and `SHARE_KEY` and `SHARE_KEY_PREVIOUS` likewise.

## Answering an abuse report

Every tool call writes one record to the Analytics Engine dataset `agentic_seo_check_calls`, kept for three months: `index1` and `blob3` the hostname audited, `blob1` the tool (`web_audit_page` for a run of the website's form), `blob2` the outcome (`ok`, `refused`, `error`, `limited`), `double1` the duration in ms, `double2` the requests sent and `double3` the pages audited. No path, query or caller address. To see what the server sent a site, with a token that has *Account Analytics: Read*:

```bash
curl "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/analytics_engine/sql" \
  --header "Authorization: Bearer $TOKEN" \
  --data "SELECT timestamp, blob1 AS tool, blob2 AS outcome, double2 AS requests, double3 AS pages
          FROM agentic_seo_check_calls
          WHERE index1 = 'www.example.com' AND timestamp > NOW() - INTERVAL '7' DAY
          ORDER BY timestamp DESC"
```

Reports come in through [help.rivi.software/contact](https://help.rivi.software/contact).
