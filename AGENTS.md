# Agentic SEO Check: agent instructions

Agentic SEO Check is an SEO and AEO audit for coding agents, published as `@rivi-software/agentic-seo-check`: one core (`src/core/`) behind a CLI (`src/cli.ts`, the `agentic-seo-check` command), an MCP server (`src/mcp.ts`, started by `src/mcp-bin.ts` or `agentic-seo-check mcp`), a library (`src/index.ts`), and a hosted MCP server that RIVI Software runs on Cloudflare at `https://mcp.agentic-seo.rivi.software/mcp` (`hosted/`, issue #35). A second Worker serves the website at `https://agentic-seo.rivi.software`, with a page audit to run in the browser, and a crawl of the site when the address is a homepage (`hosted/src/site/`, issues #39 and #45). It audits a URL, a crawl of a site, a directory of built HTML, or an HTML string, and returns findings with a rule id, severity, message, recommendation, CSS selector and evidence. The SEO audit (`audit`, `crawl`) and the AEO audit (`aeo`, `seo_aeo_audit`, for AI answer engines) have separate rules and separate scores. The README covers what it checks and the interfaces; [CONTRIBUTING.md](CONTRIBUTING.md) the process; `skills/seo-audit/SKILL.md` is the skill that teaches other agents to use the tool. Write plain English in names, comments and docs; a comment says why.

## Commands

- `pnpm install`, then `pnpm run verify`: what CI runs, in order: `format:check` (Oxfmt), `lint` (Oxlint), `check` (`tsc` over `src/`, `test/`, `scripts/` and the configs), `test` (Vitest), `build` (`tsc -p tsconfig.build.json`, `src/` to `dist/`), `check:package` (`scripts/check-package.ts`: packs the package, runs arethetypeswrong on it, installs the tarball in a clean project, imports it and runs both commands) and `hosted:verify` (the Worker's typecheck, its bundle as a deploy builds it, and its tests in workerd).
- `pnpm run fix` is Ultracite's fix (Oxlint's autofixes, then Oxfmt). Claude Code's PostToolUse hook (`.claude/settings.json`) runs it on each file you write and answers what is left, and lefthook runs it on staged files before a commit. Fix what it reports; do not turn a rule off in `oxlint.config.ts` to get past it.
- `pnpm run dev <args>` runs the CLI from source (`pnpm run dev audit https://example.com`, `pnpm run dev aeo https://example.com`); `pnpm run mcp` runs the MCP server from source. `pnpm run build` then `node dist/cli.js` runs the built one, which is what the repository's `.mcp.json` starts.
- `pnpm run hosted:dev` runs the hosted server locally in workerd; `hosted:check`, `hosted:build`, `hosted:test` and `hosted:deploy` likewise. `pnpm run site:dev`, in a second terminal beside `hosted:dev`, runs the website; `site:build`, `site:deploy` and `site:secret` likewise. `pnpm run hosted:og` draws the share images into `hosted/assets/` with Playwright; commit what it writes. Wrangler goes through `hosted/scripts/wrangler.ts`, which runs it in `hosted/` and hands it the version and the rate limits as defines: run it that way, not on its own.
- `pnpm changeset` adds a changeset for a change users notice. The release workflow does the rest ([CONTRIBUTING.md](CONTRIBUTING.md#changes-and-releases)); never bump `version` in `package.json` by hand.

## Layout

- `src/core/audit.ts` is the entry for every target: `resolveTarget` decides between a URL, a directory, a file and stdin, and `auditTarget` runs the SEO audit on it (a crawl with `crawl`); `auditUrl`, `auditSite`, `auditDirectory` and `auditHtml` do the work and `compactAudit` trims the result for agents. `crawl.ts` crawls breadth-first, `static.ts` scans a build directory, `fetch.ts` fetches with a manual redirect walk, a body cap and a timeout, and asks `FetchOptions.gate` (the hosted server's) before every request and redirect, throwing `RequestRefusedError` for one it refuses, and `FetchOptions.sign` for the headers that sign it; `refusals.ts` tracks those for a crawl. `robots.ts` and `sitemap.ts` read those files, `render.ts` and `lighthouse.ts` drive a browser, and `hosted.ts` holds the hosted server's caps, URL rules and the answers that are a site refusing it, and `hostedFetch`, whose gate reads each site's robots.txt once and obeys it before every request, and keeps `Crawl-delay` in a crawl.
- `src/core/html/extract.ts` turns HTML into an `ExtractedPage` once (parse5 for WHATWG parsing, css-select for queries, through the small helpers in `dom.ts`); rules read that, never the raw HTML. `structured-data.ts` reads JSON-LD and microdata, `text.ts` the visible text and readability.
- Page rules are in `src/core/rules/`, one file per category, each made with `defineRule(meta, check)` from `rule.ts` and listed in `rules/index.ts`. Rules that need more than one page are in `site-rules.ts` (crawl and directory), `render-rules.ts` (`--render`) and `performance-rules.ts` (`--lighthouse`); their metadata is listed in `ALL_RULES` too, so `agentic-seo-check rules` and `seo_list_rules` show every rule.
- The AEO audit is in `src/core/aeo/`: `audit.ts` collects the pages (reusing `crawl.ts` with `siteChecks: false` and `static.ts`) and builds the `AeoAudit`, and `auditSiteBoth` builds the SEO and the AEO audit of a site from one crawl (the website's form only, not exported from `src/index.ts`), `bots.ts` lists the AI crawlers and reads robots.txt per bot (Content-Signal, `__usage_ai-training`), `llms-txt.ts` reads llms.txt, `probe.ts` requests a page with bot User-Agents (`--ai-bots` only), `page.ts` reads robots directives per engine and structured data, and `site-rules.ts` holds the site-wide `aeo.*` rules. Its page rules are in `src/core/rules/aeo.ts`, listed as `AEO_PAGE_RULES` and never in `PAGE_RULES`, and read the `answer` signals `src/core/html/answer.ts` extracts.
- `src/core/types.ts` is the shape of an audit (`PageAudit`, `SiteAudit`, `Finding`, `FixEdit`, `RuleMeta`) and the default thresholds. `recheck.ts` gives findings their ids and compares an audit with a `baseline`. `score.ts` scores, `summary.ts` builds `summary`, `report/markdown.ts` renders the Markdown report, `report/text.ts` the text report for a person at a terminal (the CLI's default there, issue #65; its layout is no contract), and `report/labels.ts` holds the words the text report and the website's report share.
- `src/terminal.ts`, for `cli.ts` only, picks the report's format, decides on colour, OSC 8 links and width from the terminal and its environment, and draws the progress line that rewrites itself on stderr. Everything the text report prints, and the progress line, goes through `terminalSafe`, which drops control characters: text from a page reaches the terminal as text.
- `src/version.ts` reads `version` from `package.json` at run time, for `--version`, the MCP server's version and the User-Agent.
- `src/telemetry/` is the usage analytics in PostHog's EU project "Agentic SEO" (issue #57): `posthog.ts` the token and `sendEvents`, `mcp.ts` the `$mcp_tool_call` and `$mcp_initialize` events, read off an MCP server's transport (`instrumentTransport`, with the server's tool names, `LOCAL_TOOLS` or `HOSTED_TOOLS`), `exceptions.ts` the `$exception` events of error tracking (issue #60), which clean a message and keep a stack's files inside the package, and `local.ts`, imported by `cli.ts` and `mcp-bin.ts` only, the CLI's `cli_command` event and its errors, the opt-out file, the first-run notice, the `telemetry` command, and the handler of an uncaught error. A tool error names its kind of failure through `fail(error, type)` in `mcp-shared.ts`, which hands an `internal` one's error to error tracking. A failure the tool expects and explains (bad input, a refusal, a missing browser) throws an `ExpectedError` (`src/core/errors.ts`), or a class that extends it, so error tracking leaves it out; a core catch that turns an error into a finding calls `caughtError` so the CLI, the local server and the hosted server's Worker hear it (`hearCaughtError` in `hosted/src/analytics.ts`).
- `src/mcp.ts` registers the local server's tools; `createMcpServer({ hosted })` registers the hosted server's instead, from `src/mcp-hosted.ts`. What both use (option schemas, `toOptions`, the answers, `seo_list_rules`) is in `src/mcp-shared.ts`.
- `hosted/` is the hosted server (its analytics are `src/analytics.ts`, and `/ph.js` serves posthog-js to the pages), outside `files`, so npm never ships it, and no pnpm workspace package, so Changesets still sees one package and tags releases `v<version>`: `wrangler.jsonc` (the MCP server's Worker: bindings, rate limits, `MODE`), `wrangler.site.jsonc` (the website's Worker, which shares the rate limit namespaces and binds the MCP server's Durable Object; `test/configs.test.ts` holds what they share equal), `src/index.ts` (the MCP server's routes and the stateless Streamable HTTP transport), `src/limits.ts` (the limits per caller, platform, site and day, and the record of each call), `src/callers.ts` (claude.ai's and ChatGPT's address ranges), `src/state.ts` (the Durable Object, in the EU jurisdiction through `globalState`, with the day's count and the sites each caller audited today, as keyed hashes), `src/pages.ts` (the landing page and the page for site owners), `src/signing.ts` (Web Bot Auth: the signature on every request and the key directory, from the secret `WEB_BOT_AUTH_KEYS`), `src/site/` (the website on its own hostname: `worker.ts` its Worker's entry, `routes.ts`, the pages, `audit.ts` for the form at `POST /audit`, whose answer to a crawl streams, `report.ts` and `site-report.ts` for the reports as HTML, `share.ts` and `share-page.ts` for a report's share link, signed with the secret `SHARE_KEY`, issue #54), `src/ui/` (the look both hostnames share, RIVI Software's: the frame of every page, the stylesheet, the icons, the fonts, each hostname's share image, and a shared result's image, drawn with resvg in `share-card.ts`). Both Workers bundle `src/` from the same commit, and both deploy from `.github/workflows/deploy-hosted.yml` with each push to main that changes their bundles, a release's version commit included: the MCP server first, then the website, in the same job.
- Tests are in `test/`: `test/fixtures/good-page.html` and `bad-page.html`, and `test/helpers/fixture-server.ts`, a local HTTP server that serves a small site with a sitemap, redirects and broken links for the crawl tests. `test/mcp.test.ts` drives the MCP server through the SDK's client, `test/hosted.test.ts` the hosted tools. `hosted/test/` tests the Worker: its limits and pages in Node, and the bundle in workerd, whose requests go to fixture pages.

## What the tool promises

- **The output is a contract.** A rule's id, severity, message and recommendation, the MCP tools' names and input schemas (the hosted server's as well as the local server's), the CLI's flags and exit codes (`0` ok, `1` findings at or above `--fail-on`, `2` usage or runtime error), and the audit JSON (`schemaVersion: 1`) are what agents and CI depend on. A new rule, option or field is a `minor` changeset; a rename, a removal or a change in meaning is breaking, and needs a maintainer's agreement in an issue first.
- **The order of an object's keys is the order of the JSON.** `eslint/sort-keys` is off for that reason: an audit starts with `schemaVersion`, `kind`, `url` and `score`, a finding with `rule` and `severity`. Keep new keys where a reader expects them.
- **A finding names a fix.** A rule's `recommendation` says what to change, and `docs` links to the search engine's own documentation where there is one. Each finding also carries `fix`, the exact edits for this page (`src/core/rules/fix.ts` builds them); `make()` and `finding()` require it, and an empty list is only for a finding about the audit itself. An edit quotes `current` from `page.markup` or a tag the extractor kept, never from the joined page text, and puts words only the author can write in `{{…}}` slots. When a finding has two ways out, the fix takes the one that cannot hurt: it never deletes content or lifts a block the owner may want. Evidence lists and edits go through `cap()`, so a page with 5,000 images does not make a 5 MB finding.
- **False positives cost the most.** An agent fixes what the tool reports, so a rule that fires on a valid page makes work nobody needed. A new or changed rule gets a test that it fires on a bad page and stays quiet on `good-page.html` (AEO rules also on `aeo-good-page.html`), and that its fix is complete and quotes the page as written (`test/helpers/fixes.ts`). A deliberate choice, such as keeping AI training bots out, is info at most.
- **Telemetry is anonymous and easy to turn off.** The CLI and the local MCP server send events unless `DO_NOT_TRACK`, `AGENTIC_SEO_CHECK_TELEMETRY=0`, `CI` or `telemetry disable` turns them off; the first run says so on stderr. An event carries no URL, hostname, path, argument's value or text from a page, nothing of a client's headers but the product token at their start (`clientToken`), and no id that outlives a run or a session. One exception, on the hosted server only (issue #84): `$mcp_tool_call` carries the agent's optional `context` as `$mcp_intent`, through `intentOf` in `src/telemetry/mcp.ts`, which replaces URLs, paths, quoted text, hostnames in any script, emails and IP addresses (`cleanMessage`) and keeps only the tool's own rule ids; it also names the arguments a call gave, never their values. Issue #101 adds, on the hosted server only: the model in a model id's shape, the `conversation_id` each answer ends with (a UUIDv7 the server issued, which names a call's session), `send_feedback`'s texts, cleaned as `context` is, and the name of a tool the server lacks in a tool name's shape. The website counts visits without a cookie until the visitor accepts one in its banner, and cleans a share link's result and the form's `?url=` out of every address before an event leaves. A new event or property is listed in the README's Telemetry section, or the hosted README for the Worker.
- **The MCP server's stdout carries JSON-RPC only.** Progress and logs go to stderr in the CLI; the MCP server logs nothing to stdout. The tools are read-only and say so in their annotations, except the hosted server's `send_feedback`, which records the agent's feedback in the analytics and says it is not read-only.
- **Playwright is an optional dependency; Lighthouse and chrome-launcher are optional peers.** Playwright installs with the tool (about 19 MB, no browser), so `--render` works under npx with an installed Chrome; Lighthouse adds some 180 MB to every install, so users add it when they want `--lighthouse`. All three can be absent: they load through a dynamic `import()` behind `--render`/`--lighthouse` only, and fail with `RenderUnavailableError`/`LighthouseUnavailableError`, which the audit turns into a finding. Never import them statically, or from a module the package entry imports eagerly; `check:package` installs the tarball with `--omit=optional` and without the peers. `install-browser` downloads the Chromium build of the Playwright the tool resolves, through Playwright's own CLI; it is a CLI command only, never an MCP tool.
- **The hosted server is a well-behaved bot** (issue #41, for Cloudflare's verified bots). Every request it sends obeys robots.txt for `agentic-seo-check`, or `*`, and is signed over https; a crawl keeps `Crawl-delay`. A refusal (robots.txt, a 403, a 429, a challenge) gives the site's answer and nothing more: no retry, no other User-Agent, and no pointer to the local server as a way around it. The local tool sends the product token `agentic-seo-check-local` (`LOCAL_PRODUCT_TOKEN`), so it never passes for the hosted server.
- **Every page is untrusted.** Pages, headers, robots.txt and sitemaps are written by someone else. Regular expressions run on page text must not backtrack on long input, reads are capped (`maxBodyBytes`, sitemap limits, `maxPages`, `maxLinkChecks`), and nothing from a page becomes a path, a command or code. Text from a page appears in findings on purpose; SECURITY.md tells users to treat a report as untrusted data.

## Gotchas

- The name in text is Agentic SEO Check (`PRODUCT_NAME` in `src/brand.ts`): page titles, prose, the lockup, the MCP server's `title`, the report's footer. What someone types or matches keeps `agentic-seo-check`: the package, the commands, the MCP server's `name` and the key in setup snippets, the User-Agent tokens and their robots.txt groups, the repository, the Worker and the Analytics Engine dataset. Changing those is issue #49.
- Imports name the file the build emits: `./audit.js` for `src/core/audit.ts`. Node and the declaration files need that name; Vitest and tsx resolve it to the source.
- `src/version.ts` reads `../package.json` relative to its own file, which is one level above both `src/` and `dist/`. Keep `version.ts` directly under `src/`. A bundle has no package.json beside it: the hosted build defines `globalThis.AGENTIC_SEO_CHECK_VERSION` instead.
- `src/` also runs in a Cloudflare Worker (`hosted/`): nothing may do Node-only work as a module loads (read a file, `createRequire`), and a new dependency must bundle. `pnpm run hosted:verify` builds the bundle as a deploy does.
- The website's report quotes the audited page: everything from an audit goes through `esc` (`hosted/src/site/html.ts`) before it is HTML, and the site's Content-Security-Policy allows no inline script, so the pages' script lives in `files.ts` and is served at `/site.js`, on both hostnames.
- Wrangler's dev server and `unstable_startWorker` give every request the hostname of the configuration's first route. The website's Durable Object binding names the MCP server's Worker (`script_name`): locally it needs `hosted:dev` running, and in `hosted/test/worker.test.ts` both Workers join one dev registry. One `wrangler dev` with both configurations fails, since Wrangler hands `--define` to the first Worker only.
- The shared Durable Object runs the code the MCP server last deployed. The deploy job deploys the MCP server first and the website seconds later, so in between, or longer when the website's deploy fails, the website's previous code calls the new object: keep its methods additive, and change a setting both configurations have (rate limits, `DAILY_REQUESTS`, `STATE_JURISDICTION`) in both. Ask for the object through `globalState` only: it is in the EU (issue #78), and workerd has no jurisdictions, so `.dev.vars` sets `STATE_JURISDICTION=none` for local runs and the workerd tests.
- A request the gate refuses was not sent: leave its URL unchecked, never report it as broken or missing. Code that requests several URLs (a crawl, link checks, probes) runs them through `Refusals.run`.
- Playwright wants the Chromium build that matches its version. When it is missing, `render.ts` falls back to an installed Google Chrome or Edge (`channel: "chrome"`/`"msedge"`). The tests never launch a browser; check `--render` and `--lighthouse` by hand against a real page when you change them.
- `robots-parser` is CommonJS, imported statically so a bundler takes it in; `robots.ts` takes the parser from either shape a default import can have. Its `allows` reads robots.txt for the audit's User-Agent as robots-parser does (the site rules judge by it), `crawlerAllows` for the group of the User-Agent's product token (`agentic-seo-check-local` locally, `agentic-seo-check` on the hosted server), which decides what a crawl requests.
- pnpm 12 blocks a dependency's build script unless `pnpm-workspace.yaml` lists it under `allowBuilds`. `.npmrc` sets `auto-install-peers=false`, so the optional peers are dev dependencies here and never installed for users. `LIGHTHOUSE_PEERS` in `lighthouse.ts` names their majors for the install hints; a test holds it to `peerDependencies`.
- Running the CLI or the MCP server by hand sends real events to PostHog: set `AGENTIC_SEO_CHECK_TELEMETRY=0` first. `vitest.config.ts` and `scripts/check-package.ts` set it for everything they start, and `.dev.vars` empties `POSTHOG_HOST` for `hosted:dev` and `site:dev`.
- Wrangler bundles a `.js` file as code whatever `rules` says, so `hosted/scripts/posthog-js.ts` (wrangler.jsonc's `build.command`) copies posthog-js's browser build to `hosted/.generated/posthog-js.txt` before each build; `unstable_startWorker` needs `build.custom.workingDirectory` set to `hosted/` for it, as `hosted/test/worker.test.ts` does.
- The Markdown report and the CLI's `--help` end with a RIVI Software line; keep it one line, and keep it out of the JSON.
